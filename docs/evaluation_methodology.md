# Evaluation Methodology

How SITA's detection rules, IOC extractors, correlation logic, and AI-assisted triage are measured for correctness against a held-out dataset. See [DEF.md § Phase 12](../Documentation/DEF.md#phase-12-performance-and-evaluation) for the field-level schema this document assumes, and [PHASE-12.md](../Documentation/PHASE-12.md) for the full build narrative.

## Why a second dataset

`data/synthetic_events/` (Phase 2) is what the detection rules' thresholds (Phase 3), the IOC extractors' patterns (Phase 4), and the correlation weights (Phase 5) were written and hand-verified against. Measuring precision/recall against that same data would answer "does the code do what it was tuned to do" — circular, and not a real accuracy claim.

`data/eval/` is a second, independent dataset: different hosts, IPs, usernames, and timestamps throughout (a distinct epoch, `2026-03-01`, versus the dev dataset's `2026-01`). It's generated by a checked-in script (`backend/app/evaluation/generate_dataset.py`) rather than hand-written — deliberately, not as a shortcut: the same function that emits a case's events also emits its ground-truth label, so the two structurally cannot drift out of sync the way a hand-transcribed label file could. The generator is reviewable as code; its *output* (the JSONL event files and `ground_truth.json`) is what's checked in and what the evaluation harness actually reads at run time — running an evaluation never depends on regenerating data first.

**One honest limitation**: `impossible_travel`'s `StaticGeoIPResolver` (Phase 3) only knows a fixed, small set of IP-to-location mappings — a documented stub, not a real GeoIP database. The eval dataset's `impossible_travel` cases have to reuse those exact IPs; there's no way to build a genuinely held-out case for that one rule without either reusing the stub's known addresses or extending the stub itself. Every other identifier, and every other rule, is independent of the dev dataset.

## Dataset construction

33 detection cases across all 7 detection rules — 3 positive + 2 negative per rule, except `impossible_travel` (2 positive + 1 negative, constrained by the GeoIP stub above). 12 IOC cases — one positive case per `IOCType` (9 types) plus 3 explicit negative cases targeting extractor filtering logic specifically (a private IP in free text, a `.internal` domain in free text, a malformed/short hex string). 2 correlation cases — one multi-stage attack expected to merge into a single incident, one pair of unrelated events expected to stay separate.

**Case-to-event attribution** doesn't parse rationale text or guess from time windows. Every case gets a unique marker — a host name, IP, or username baked into its events at generation time and unlikely to collide with anything else in the dataset. The harness finds a case's own events by querying for that exact marker, then checks which alerts/incidents those specific events landed in. This is robust to how a rule's rationale happens to be worded, or to timing coincidences with unrelated cases.

### Bugs the dataset construction itself caught

Building the generator surfaced three real bugs before any evaluation number was ever computed — worth stating, since a generator that produces a subtly wrong dataset is worse than no dataset at all:

1. **Cross-case contamination.** The `password_spraying` positive/negative cases originally shared one host. `repeated_auth_failures` groups by host, so the cases pooled together and produced false positives. Fixed by giving every `password_spraying` case its own unique host.
2. **Threshold collision.** One `password_spraying` positive case used exactly 10 single-attempt users — which also happened to cross `ssh_brute_force`'s own ≥10-failure threshold, producing an unintended false positive. Judged an arbitrary parameter collision (not a meaningful rule overlap worth preserving) and fixed by dropping to 9. This is a different situation from `impossible_travel` and `suspicious_auth_pattern`, which *do* genuinely, structurally overlap (impossible travel's precondition — a new IP for an established user — is also literally suspicious_auth_pattern's own signal) — that overlap is real and is kept, explicitly excused via each affected case's `also_expected_rule_keys` rather than treated as noise.
3. **Source-type typo.** The `ioc_ipv6` case declared `source_type="network"` but was built with the DNS event helper — a copy-paste bug. NETWORK ingestion silently rejected the DNS-shaped payload, so the case never actually reached the pipeline. Found by noticing the generated `dns.jsonl` had one line where two were expected, then tracing back to the constructor call. Fixed to `source_type="dns"`.

All three were caught by running the generator and inspecting its actual output, not by reasoning about the code — consistent with this project's established "verify, don't assume" discipline from every prior phase.

## Metrics

### Detection: precision / recall / F1, per rule and overall

A case counts as a true positive only if an alert from its *own expected rule* matched its *own events* — not merely if some alert fired somewhere in the run. Any other rule firing against a case's events counts as a false positive, unless that rule is explicitly excused via `also_expected_rule_keys` (the impossible-travel/suspicious-auth-pattern overlap above is the only case where this applies).

### IOC extraction: precision / recall, per `IOCType` and overall

Evaluated per case, not as a global set comparison. An earlier design compared the full set of extracted IOCs against the full set of expected IOCs across the whole dataset and produced misleadingly low precision — as low as 2.3% for `ipv4` — because every legitimately-extracted IOC that simply wasn't in the expected list (e.g. every auth event's own `source_ip`, present but not "the point" of that case) counted as a false positive. That measures "did you enumerate every IOC in the dataset," which was never the question. Caught before publishing any number, and redesigned: each case now checks only its own event's extracted `(ioc_type, value)` pairs against that case's own expected pair (for positive cases) or forbidden pair (for negative cases, which must be absent).

### Correlation: correct grouping rate

For each correlation case, whether the final incident graph matches its `expect_single_incident` label — the multi-stage case's alerts should all land in one incident; the unrelated-pair case's alerts should land in two.

### AI-generated triage: automated grounding, not manual rubric scoring

This resolves TODO.md's open question, "How to evaluate AI-generated triage." Manual 1–5 rubric scoring was never really available here — this project's actual workflow is an agentic session, not a staffed evaluation team with a human rater, and pretending otherwise would mean either skipping the check or fabricating scores. Automated checks instead:

- **Grounding**: does an `incident_summary` or `investigation_hypothesis` output mention at least one of the incident's real entity/IOC identifiers? This is a weak-but-real signal against wholesale hallucination — it doesn't grade *quality*, only whether the output is actually anchored to this incident's data.
- **MITRE overlap**: does `mitre_suggestion`'s technique set overlap with the deterministic, rule-mapped techniques Phase 8 already computes for the same incident? Rule-derived mappings are ground truth here; the LLM is being checked for agreement with a signal that doesn't depend on it.

This only produces a meaningful number against a real model — `MockProvider`'s canned text isn't grounded in any specific incident's data, so evaluating it would measure the fixed test string, not the model. The harness runs this opportunistically against a live `OllamaProvider` when one is reachable (the same pattern established in Phase 6's `test_llm_ollama_live.py`), and states plainly when it's skipped rather than reporting a number computed against Mock as if it meant something.

### Correlation

2/2 cases correct (accuracy 1.0): `multi_stage` merged into a single incident; `unrelated_pair` stayed as two.

**Why near-100% is the expected, correct result, not a red flag**: the eval dataset is built to the *same specification* the rules were designed against (same field shapes, same rule thresholds, same correlation signals) — it just uses independent identifiers and timestamps. Perfect scores here demonstrate the rules generalize past the exact dev fixtures they were originally checked against, not that the rules are flawless against real-world noise, edge cases, or adversarial evasion. That's a meaningfully weaker claim, stated as such rather than oversold.

### AI grounding (live Ollama run)

Run against the eval dataset's `multi_stage` incident (SSH brute force → port scan → PowerShell), using `qwen2.5:0.5b` — a small model chosen for fast hand-verification, **not** the project's recommended default (`llama3.1:8b-instruct-q4_K_M`, see `.env.example`). All 6 triage tasks returned schema-valid, structured output:

| Metric | Result |
|---|---|
| Tasks returning valid structured output | 6 / 6 |
| Per-task latency | 533 – 3906 ms |
| Prompt tokens per task | ~1200 – 1251 |
| Completion tokens per task | 58 – 317 |
| Grounding rate (summary/hypothesis text) | 0.0 (0 / 5) |
| MITRE overlap rate | 1.0 (1 / 1) |

Two genuine findings, reported as observed:

- **`attack_classification` hallucinated.** The model's output included `"category": "ransomware"` — nothing in the incident's data supports that; the actual scenario is brute-force credential access followed by reconnaissance, with no ransomware indicator anywhere in the events, alerts, or IOCs.
- **Grounding rate was 0%.** None of the five checked text outputs (summary + hypotheses) mentioned any of the incident's real entity or IOC identifiers by value — the model produced fluent, schema-valid text that wasn't actually anchored to the specific data it was given.
- **MITRE overlap was 100%.** The one technique the model suggested did match a deterministic, rule-mapped technique (`T1110.001`, valid accounts / brute force) — a positive result, though from a sample size of one suggestion.

This is exactly the failure mode the "LLM is never the sole source of truth" principle (see the root `CLAUDE.md`) exists to guard against, and it's real, measured evidence of why: a 0.5B parameter model, chosen for fast local verification rather than quality, produced text that read as confident and well-formed while failing to ground itself in the specific incident and inventing an attack category with no supporting evidence. This is not evidence against the recommended 7–8B default (untested here, and a materially different model class) — it's evidence for why deterministic rules, not LLM output, own detection, severity, and correlation, and why every AI claim in this project is persisted as a labeled, separately-attributable `AnalysisResult` rather than merged into deterministic fields.

## Reproducing this

```bash
cd backend
uv run python -m app.evaluation.generate_dataset   # regenerate data/eval/ (only if the generator changes)
uv run python -m app.evaluation.cli                 # run detection/IOC/correlation evaluation
uv run pytest tests/integration/test_evaluation_harness.py -q   # regression-locked version
```

The AI-grounding run requires a locally running Ollama instance with the target model pulled; it is not part of the automated test suite (opt-in, opportunistic — see [DEF.md § Phase 6](../Documentation/DEF.md) for the established pattern this follows).
